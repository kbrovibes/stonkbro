# v0.43.1 — Portfolio access approval could silently half-fail

## What broke
The first real-world approval in production left `portfolio_access_requests` marked `approved` with no row in `user_snaptrade_credentials` at all. `POST /api/admin/portfolio-access` wrote the `approved` status first, then called `registerSnapTradeUser` + `storeUserSnapTradeCredentials` — when that second step failed, the response was a 500, but the DB write from the first step had already committed. From the admin's side this looked like "nothing happened when I clicked Approve," and worse, the request then vanished from both the alert banner (once acknowledged) and the Settings pending list (`listPendingRequests` only returns `status='pending'` rows) with no way to retry — the requester was stuck approved-but-uncredentialed forever.

## Fixes
- `src/app/api/admin/portfolio-access/route.ts`: SnapTrade registration now happens *before* the status write. A failure leaves the request `pending` and returns a real error, so retrying is just clicking Approve again.
- `src/components/AlertBanner.tsx` and `src/app/(app)/settings/AdminAccessSection.tsx`: a failed decision now shows the actual error message instead of doing nothing. The clicked button's label also switches to "Working…" while in flight, so it's clear which of Approve/Deny actually fired (both dim together by design, to block a double-submit — a shared disabled state that had read as "both got clicked").
- The one production request that hit this was reset from `approved` back to `pending` directly in Supabase, so it can go through the fixed flow.
