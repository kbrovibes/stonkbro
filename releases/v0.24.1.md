# v0.24.1 — Bloodbath cron + caching

## Problem

`/bloodbath` ran a live scan on every load: ~60 Tradier history fetches + quote batch (multi-second), then an authed AI call for verdicts (more seconds, tokens per load).

## Fix

- **`bloodbath_scans` table** (migration `20260728_bloodbath_scans.sql`, applied to prod): full scan JSON (`watchlist`, `market`), `verdicts`, AI provenance, status, duration. RLS mirrors `csp_scans` (authenticated read, service-role manage).
- **`/api/cron/bloodbath`** (CRON_SECRET bearer, maxDuration 300): scan over union of ALL users' watchlist symbols (cron has no session; effectively single-user app) + universe → `pickVerdictTargets` (watchlist first, cap 12) → one batched AI call → one completed row. Verdicts are best-effort: an AI failure still stores a usable scan.
- **Schedules** (vercel.json): 13:45, 17:00, 20:10 UTC weekdays — post-open, midday, post-close.
- **`GET /api/bloodbath`**: serves latest completed row ≤72h old (covers weekends) with `cached: true` + `timestamp` + embedded `verdicts`; falls back to a live scan when the cache is empty/stale or on `?refresh=1` (live scans don't include verdicts — the page then calls the verdict route as before).
- **Page**: uses embedded verdicts (zero AI calls on cached loads), "as of Xm ago" label, Refresh button for a live re-scan.
- **Refactor**: verdict prompt/parse moved from the route into `src/lib/analysis/bloodbath-verdict.ts`; shared by cron and `POST /api/bloodbath/verdict` (unchanged contract).

## Verified

Local cron run against prod DB: 102 scanned, 37 watchlist, 11 market drops, 12 verdicts in 37s. Cached GET: 200 in 0.38s with verdicts embedded.
