# v0.43.0 — Daily Briefing: reliable audio, single playlist, auto-play

## Summary
The Daily Briefing player gets two kinds of fix: a root-cause fix for why two of every three episodes had no audio, and a UI pass matching how the user actually wants to listen — one playlist instead of day sections, tap-to-play cover art, prev/next episode buttons, and auto-play with a 3-state control.

## Why "Audio unavailable" kept showing up

Querying the last two weeks of `daily_briefings` showed a stark, consistent pattern: every single `premarket` session had audio; every single `midday` session failed with `TTS failed: TTS timed out after 90s`; every single `close` session failed with `TTS failed: Stream closed before the synthesis completed (no turn.end received)`. This wasn't random flakiness — it was deterministic per session, going back at least to September 9th.

The tempting explanation — midday/close transcripts are longer — didn't hold up: `premarket` transcripts ranged 2387–2896 chars, `midday` 2631–3191, `close` 2260–2911. The ranges overlap; length alone doesn't explain a 100%/0%/0% success split. The free Microsoft Edge "Read Aloud" endpoint (`msedge-tts`, no API key, unofficial) is just unreliable on a single long synthesis call, for reasons its lack of documentation doesn't explain.

**The fix**: rather than guess at an exact length threshold to target, `src/lib/briefing/tts.ts` now splits the transcript into small, sentence-aligned chunks (~450 chars, never splitting a sentence), synthesizes each chunk independently with its own connection and up to 2 retries, and concatenates the resulting MP3 buffers. Verified directly against the free endpoint with a synthetic ~2.7k-char transcript: 8 chunks, each returning in under a second (the first ~4s for connection setup), for a fully reliable ~10s total synthesis with zero failures.

**Backfilling what already broke**: a new route, `src/app/api/cron/briefing-backfill/route.ts` — deliberately **not** on any cron schedule, bearer-authenticated with `CRON_SECRET` — re-runs TTS on every completed briefing that has a transcript but no audio (`listMissingAudio` in `src/lib/db/briefings.ts`), reusing the already-written transcript rather than re-gathering context and re-calling the AI. Triggered once manually after deploy to backfill the affected recent episodes.

## Daily Briefing player UI

- **One playlist, not day sections**: `BriefingPlayer.tsx` previously rendered a `playlistGroups` structure with a date header per day. Flattened to a single newest-first list; each row now shows its date inline (`fmtDateShort`) alongside session and time, since there's no header to carry that anymore.
- **Album art is play/pause**: the cover image is now a button with a hover/tap play or pause overlay, rather than static decoration next to the actual controls.
- **Prev/next episode buttons**: added alongside the existing 15-second skip buttons. They walk a `flatQueue` — every episode with audio, sorted chronologically — independent of whatever auto-play mode is set, since a manual tap is a deliberate action.
- **Auto-play on page load**: the newest episode attempts to start playing as soon as the player has one to play. A rejected `play()` (browsers routinely block autoplay without a prior user gesture) is now handled silently — the episode loads and sits ready to tap, no error shown — versus before, where there was no autoplay attempt at all.
- **3-state auto-advance control**: a new pill button cycles `same-day` (default — continue within the day, stop at the last episode) → `across-days` (keep going into earlier days) → `off` (stop after the current clip), persisted to `localStorage` (`briefing-autoplay-mode`) and read back on mount via an effect (not a `useState` lazy initializer, to avoid an SSR/client hydration mismatch on the button's label).
