# v0.24.4 — Fix SnapTrade 429s in deep activity fetches

## Problem

`POST /api/portfolio/time-machine/backfill` consistently returned
`500: Request failed after 3 retries due to 429 (rate limit) errors.`

The failure originates in `getAllActivities()` → `fetchActivitiesWindow()`
(`src/lib/snaptrade/client.ts`). The recursive window-splitter fetched both
halves of every split with `Promise.all`, and `getAllActivities` additionally
fanned out over all accounts in parallel. As transaction history grows, each
extra split level doubles the concurrent request count, so the deep
2010→today walk now bursts past SnapTrade's per-minute rate limit on its own.
The SnapTrade SDK retries a 429 only 3 times with 5s/10s backoff (~15s
total), which lands every retry inside the same exhausted rate-limit minute —
so the whole request fails even though a slower call pattern would succeed.

## Fix

- `fetchActivitiesWindow`: recursion halves are now fetched sequentially.
- `getAllActivities`: accounts are walked sequentially.

Shallow per-account fan-outs elsewhere in the client (positions, balances,
`getOptionChains` over a 2026+ window) are unchanged — the account count is
small and those don't recurse deep.

## Trade-off

The deep history fetch is slower (sequential leaf windows instead of
parallel), but it runs inside routes with generous `maxDuration` (backfill:
300s) and now completes reliably instead of failing fast.
