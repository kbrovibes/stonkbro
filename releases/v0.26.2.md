# v0.26.2 — Push notifications actually work + privacy-lock groundwork

## Problem

No push notification had ever arrived on the user's phone — not the hourly
market-monitor alerts, not test notifications. Root-cause investigation found
two independent breaks plus three smaller defects.

## Root causes (found by live-testing production)

1. **Every deploy failing since Aug 4** — the v0.25.0 market-monitor cron
   (`0 11-23 * * 1-5`, hourly) exceeds Vercel Hobby's once-daily cron limit,
   so Vercel rejected every deployment. v0.25.x–v0.26.1 never reached
   production; the `alerts` table has 0 rows ever (the monitor never ran).
2. **`/sw.js` behind auth middleware since April** — the middleware matcher
   only excluded images, so the service-worker script fetch got a 307 to
   /login (a fatal registration error per spec) that was also CDN-cached as
   `public`. Registration errors were swallowed by a bare catch. This broke
   push delivery AND made offline-mode registration flaky.
3. Notification icon pointed at `/icon-192.png` (404; real path `/icons/…`).
4. No push-only test existed — both Settings test buttons piggybacked email
   routes that 400 without `alert_email` before ever reaching push.
5. Settings "Enabled" badge read `Notification.permission` only — it showed
   enabled even when no PushSubscription existed.

The send path itself (VAPID keys, web-push, subscriptions) was verified
healthy end-to-end against production.

## Fixes

- Market-monitor cron → `0 17 * * 1-5` (10am PT daily). Restoring hourly
  requires Vercel Pro; revert this one line after upgrading.
- Middleware matcher excludes `sw.js`, `manifest.json`, `icons/`.
- SW registration failures logged; icon paths fixed.
- New authed `POST /api/push/test` (sends to the current user's own devices,
  reports sent/failed); Settings gets a "Send test push" button, an honest
  subscription-driven status with re-subscribe path, and surfaced errors.
- `sendPushToAll` gains an optional per-user filter and logs status/body on
  non-410 failures.

## Also in this release: privacy-lock groundwork

`privacy_pin` on user_settings (migration applied), Settings "Privacy Lock"
PIN section, Lock/Unlock private info in the profile menu with an in-app PIN
modal, server-side PIN verification setting an httpOnly `pii_lock` cookie
(so RSC-rendered values can be masked), settings API stripped of the PIN and
guarded against PIN changes while locked. App-wide value masking ships next.
