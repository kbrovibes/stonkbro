# v0.24.6 — Portfolio chains cache (bloodbath-style)

## Problem

Even after v0.24.5, every Portfolio page load re-walked the full SnapTrade
activities history live: 2.6s-paced recursive window splits, sequential
accounts, and a possible 65s 429-wait — worst case minutes per load, for data
that only changes when a trade happens or an expiry passes.

## Fix

Cache the computed `OptionChain[]` server-side, following the
`bloodbath_scans` pattern:

- **`portfolio_chain_scans` table** (migration applied): one row per scan
  with the full chains jsonb, `start_date` window key, status, duration.
  RLS is service-role only — this is personal brokerage data, so there is
  deliberately no authenticated read policy; access is gated by
  `hasPortfolioAccess` in the API route (which uses the admin client).
- **`/api/cron/portfolio-chains`** (2× weekdays: 13:15 & 20:15 UTC ≈
  pre-open and post-close ET): runs `getOptionChains("2025-01-01")` and
  stores the result. `maxDuration = 300`.
- **`GET /api/portfolio?include=option-chains`** now serves the latest
  completed cached scan (≤72h, covers weekends) when `startDate` matches the
  cache window (`2025-01-01`); `?refresh=1` forces a live fetch. Live
  results (refresh or cache miss) are stored back so the next load hits the
  cache. Non-standard `startDate` values bypass the cache entirely — chain
  grouping depends on the window, so windows aren't interchangeable.
- **Page**: "as of Xm ago" freshness label + Refresh button. Refresh keeps
  existing chains on screen while the live fetch runs (it's the slow path)
  and shows an inline error on failure instead of blanking the page.
  PWA pull-to-refresh stays on the fast cached path.

## Result

Page loads are one DB read (~0.4s) instead of a live SnapTrade walk, and
routine page views no longer contribute to the activities endpoint's
per-minute rate limit at all.
