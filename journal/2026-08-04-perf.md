# Performance overhaul — 2026-08-04

Goal: the app "feels slow — fetches a lot of data, pages render slow, some pages
do live data fetch + analysis on load." This pass attacks the two costs a user
actually feels on every navigation: the JavaScript each page must download and
parse before it's interactive (First Load JS), and the server-side latency
before the first byte arrives (TTFB).

Hard constraints honored: zero behavior/calculation changes, zero visual
redesigns, no migrations touched, no options math / SnapTrade pacing / cron
changes, TypeScript strict-clean, `npm run build` green before every commit.

## How First Load JS was measured

Next 16's build no longer prints the per-route size table in this environment,
but it writes `.next/diagnostics/route-bundle-stats.json`, which lists each
route's first-load chunk paths and uncompressed byte total. "Raw" below is that
uncompressed total; "gzip" is the sum of `gzipSync` over each first-load chunk
(what the browser actually downloads). Baseline captured before any change on
the same machine.

## Before / after — First Load JS per route

(−26%)**. `/login`, `/`, and `/_not-found` are outside the app shell and
unchanged (login legitimately loads the Supabase browser client for sign-in).

## Changes and measured effect

### 1. Supabase browser SDK removed from the app shell — −59 KB gzip on all 40 app routes
`ProfileMenu` renders in `Header` on every authenticated page and imported the
`@supabase/ssr` browser client solely to call `supabase.auth.signOut()`. That
dragged the whole ~222 KB (uncompressed) Supabase client SDK into the chunk
shared by every route. Sign-out is now a server action (`src/lib/auth-actions.ts`)
invoked from a plain `<form action={…}>`; it clears the auth cookies server-side
(the same cookies middleware manages) and redirects to `/`. The unused
`LogoutButton` was converted the same way. Only `/login` still imports the
browser client, and that's correct.
Effect: −222 KB raw / −59 KB gzip on 40 routes. This is the single biggest
user-felt win because it applies to every page the user opens.

### 2. Learn lesson page rendered as an RSC — −130 KB gzip on the lesson route
`/learn/[moduleId]/[lessonId]` was `"use client"` and imported the entire
`CURRICULUM` (~3,300 lines of lesson data for all modules) just to `find()` one
lesson by id, so all of it shipped in the route's client JS. It's now a server
component that resolves the lesson server-side and hands only that lesson's
`sections` (plus metadata and prev/next ids) to a thin client island
(`LessonClient`) that keeps the scroll-save, completion-observer, and nav
interactivity. `CURRICULUM` no longer reaches the browser.
Effect: 997 → 555 KB raw, 290 → 159 KB gzip.

### 3. Auth round-trips deduplicated per navigation — server TTFB
`supabase.auth.getUser()` is a network call that validates the session JWT
against Supabase Auth — not a local decode. Every authenticated page ran it at
least three times per navigation (the `(app)` layout, `Header`, and the page),
sequentially as the server-render tree resolved. A new `getUser()` wrapped in
React `cache()` (`src/lib/auth.ts`) memoizes for the duration of one request;
the layout, header, and 14 page components now share a single round-trip, and
the redundant `createClient()` cookie reads that came with each duplicate went
away too.
Effect: 3+ sequential auth round-trips → 1 per authenticated navigation.

### 4. Independent server fetches parallelized — Home and Income TTFB
- Home fetched watchlist quotes then the earnings calendar (~40 symbols)
  sequentially, though earnings depends only on the symbol list, not the quotes.
  Now one `Promise.all`.
- Income fetched positions then settings sequentially though both key only off
  `user.id`. Now parallel.
Effect: removes one full upstream round-trip from each page's critical path.

## What was checked and deliberately left alone

- **Daily client pages (today, csp-hunter, bloodbath, portfolio)** already
  fetch in parallel via `Promise.allSettled` + a `sessionStorage` TTL cache
  (`cachedFetchJson`) and already render skeletons while loading. No waterfall
  to fix there.
- **Portfolio option-chains and bloodbath** are already served from DB caches
  (`portfolio_chain_scans`, `bloodbath_scans`) — untouched.
- **Learn chart components** are already `React.lazy` inside `LessonRenderer`;
  they load on demand, not up front.
- **Dashboard / positions / risk / wheel / covered-calls** server fetches are
  genuine dependency chains (user → positions → quotes-for-those-symbols) that
  can't be parallelized without changing what's fetched. `covered-calls`
  already uses `Promise.all`/`allSettled` internally.

## Further work (not done this pass)

- **App-shell shared chunk floor (~156 KB gzip)** is now react-dom (~222 KB raw)
  + the Next framework runtime (~137 KB raw) + the shell client components
  (BottomNav, AlertBanner, PullToRefresh, ProfileMenu, theme providers, SW
  registration). The framework/react portion is fixed; the shell components
  could be audited for anything deferrable, but each is small and used on the
  first paint, so the upside is minor.
- **/login at 746 KB** carries the Supabase browser client for sign-in. It's a
  once-per-session page, so low priority, but a lighter auth path (e.g. a
  server-action credential flow) would trim it.
- **Fonts**: the root layout loads four Google font families (Plus Jakarta Sans
  ×5 weights, Geist Mono, Black Ops One, Space Grotesk). `next/font` self-hosts
  them so there's no external request, but if Black Ops One / Space Grotesk are
  used only for a few display strings, subsetting or dropping a weight would
  speed first paint. Left alone here because it risks a visible type change.
- **Large client pages (time-machine 1,646 lines, portfolio 1,276)**: their
  remaining ~30–50 KB over the shell floor is inline page logic. Splitting
  rarely-shown sections (modals, detail panels) behind `next/dynamic` could
  shave a bit more, but returns are marginal versus the wins above.
